# PAPA BOT - реестр реализованного функционала

## 2026-08-10 Профильные документы от имени пользователя

- Документы, загружаемые в разделе ПРОФИЛЬ, сохраняются User Token выбранного профиля. Для них не вызывается загрузка на стену сообщества и не создаётся вложение сообщества.
- Этот маршрут применяется и для больших файлов через Render-relay, поэтому не зависит от временных VK upload URL стены сообщества и ошибок HTTP 405.

## 2026-08-10 Резервная загрузка профильных документов в VK

- PAPA BOT сначала загружает документ согласия стандартным методом для стены сообщества. Если VK возвращает отказ «User can't upload docs to this group», сервис автоматически использует загрузку через сообщения сообщества Community Token.
- Резервный маршрут сохраняет вложение с владельцем-сообществом, поэтому документ остаётся доступен для отправки пользователям и не появляется в личных документах администратора.

## 2026-08-10 Загрузка документов профиля и сессия настроек вложений

- Документы, добавляемые в ПРОФИЛЕ для согласий, загружаются на стену сообщества с User Token именно выбранного профиля и сохраняются как документы сообщества; токен другого профиля не используется.
- Сохранение источника загрузки вложений выполняется через авторизованный запрос с действующей сессией. Сообщения об ошибке и успешном сохранении в этом блоке отображаются пять секунд и затем исчезают.

## 2026-08-09 Юридические документы VK Mini App

- Публичный юридический раздел VK Mini App приведён к фактической работе PAPA BOT и содержит три связанные страницы: Политику обработки персональных данных, отдельное Согласие и Публичную оферту.
- Политика описывает аккаунты сервиса, VK Mini App, ВКонтакте и Telegram, токены интеграций, сообщения и комментарии, рассылки, триггеры, платежи, подписки, пакеты и внутренний баланс.
- Разделены роли PAPA BOT как самостоятельного оператора данных аккаунта и как обработчика данных аудитории по поручению владельца сообщества или бота.
- Согласие оформлено отдельно от Оферты и подтверждается отдельным электронным действием с фиксируемой редакцией; формулировки о чекбоксах удалены.
- Оферта описывает авансовый внутренний баланс, покупки подписок и пакетов, бонусы, возвраты, чеки плательщика НПД и обязательные права потребителя.
- Все страницы используют email `papa.bot.1@yandex.ru`, взаимную навигацию, адаптивную вёрстку и системную светлую/тёмную тему.

## 2026-08-09 Восстановлена маршрутизация крупных загрузок через Render

- Локальные вложения и документы размером больше 3,5 МБ снова автоматически отправляются через Render, минуя ограничение тела запроса Yandex Cloud Functions.
- Для файлов до 3,5 МБ сохраняется штатная загрузка через PAPA BOT; Render сохраняет прежние повторные попытки и восстановление результата.

## 2026-08-09 Безопасная передача крупных файлов через Render-relay

- Render больше не получает User Token из браузера: админ-панель получает короткоживущий подписанный grant без секрета, а Render передаёт файл чанками обратно в PAPA BOT.
- PAPA BOT собирает чанки во временном Object Storage, получает User Token только из защищённой конфигурации и выполняет загрузку в VK на сервере; после завершения временные чанки удаляются.
- Для видео финальный серверный шаг обходит повторный вызов Render и сразу использует VK User Token; тайм-аут relay увеличен до 300 секунд для медленной обработки видео.

## 2026-08-09 Автонастройка Callback API после скрытия токенов

- Автонастройка сообщества сначала находит выбранную запись и использует сохранённые в защищённом хранилище VK Group ID, токен сообщества и User Token.
- После «Сохранить все настройки» пустые и скрытые поля браузера больше не мешают автонастройке; ошибка выводится только для действительно отсутствующих значений.
- Инструкция получения User Token теперь предлагает скопировать сгенерированную ссылку и вручную вставить её в адресную строку браузера. На отдельном сайте генератора удалена программная кнопка открытия ссылки.

## 2026-08-09 Единые лимиты в окнах ошибок и предложений

- Окна «Сообщить об Ошибке» и «Предложения» больше не показывают жёстко заданный лимит 5 в день.
- Текст в обоих окнах берёт текущий лимит выбранного профиля из dashboard: он совпадает со счётчиком «Сегодня отправлено: … из …» и настройкой активного профиля лимитов.

## 2026-08-09 Профили лимитов, тарифов и бонусов в Центре управления

- Сырой JSON-редактор заменён русскоязычной формой: бесплатный лимит, границы и уровни бонусов пополнения, каждый тариф «Подписка», каждый разовый «Пакет», а также лимиты и награды ошибок/предложений имеют отдельные поля и пояснения.
- Добавлен неизменяемо доступный профиль «По умолчанию» с исходными значениями PAPA BOT. Новый профиль создаётся как копия выбранных значений, поэтому изменение отдельных полей не обнуляет остальные.
- Профили хранятся отдельно от действующих настроек. «Сохранить изменения профиля» меняет только этот профиль, а «Загрузить профиль в сервис» по явному подтверждению применяет его к новым операциям PAPA BOT и отмечает как активный.

## 2026-08-09 Актуальная справка всех рабочих разделов

## 2026-08-09 Вход и регистрация сервиса из VK Mini App

- Центр управления теперь показывает все записи `PROJECT_COMMANDS.json`, включая безопасные инструкции по проверке и выпуску VK Mini App, её ключевые файлы и последовательность публикации.

## 2026-08-09 Финальная проверка входа и сброса пароля

- Активный серверный обработчик входа больше не передаёт в браузер текст ошибки из внутренних модулей: в форме всегда показывается понятное русское сообщение.
- После подтверждённой смены пароля удаляется старая captcha-запись для текущего устройства. Новый пароль можно использовать сразу, без прежнего требования капчи.
- Ошибки отправки кода и применения нового пароля в форме восстановления заменены на стабильные понятные сообщения без mojibake.

## 2026-08-09 Единый обработчик входа и запрет кэширования авторизации

- Третий неверный ввод теперь сразу сообщает клиенту о необходимости email-восстановления и не включает капчу вместо этого.

- После возврата из восстановления счётчик остаётся равен нулю; повторный вход возможен только после успешного задания нового пароля.

## 2026-08-09 Исправлены тексты авторизации и счётчик после возврата

- Возврат из восстановления показывает форму входа с нулём оставшихся попыток, сохраняя достигнутый лимит до успешной смены пароля.

- Старое окно блокировки больше не возвращает ручную заявку администратору; оно открывает email-восстановление. Непонятные символы в предупреждениях входа заменены на обычный текст.

## 2026-08-09 Восстановление пароля по email после трёх ошибок входа

- После успешной смены пароля блокировка входа сбрасывается, сессия не создаётся автоматически: пользователь возвращается к форме входа и вводит новый пароль.

## 2026-08-10 Регистрационные согласия и аудит профиля

- Создание нового аккаунта требует три отдельных обязательных подтверждения: согласие на обработку персональных данных, ознакомление с Политикой обработки персональных данных и принятие Публичной оферты. Ссылки ведут на опубликованные юридические страницы PAPA BOT и открываются в отдельной вкладке.
- Сервер повторно проверяет все три подтверждения до расходования кода email и создания профиля; переданные браузером названия или версии документов не используются.
- Для нового профиля вместе с датой регистрации сохраняются дата/время подтверждения, названия, редакции и постоянные ссылки принятых документов. Эти сведения показываются владельцу в начале раздела «ПРОФИЛЬ» и главному администратору в карточке каждого профиля раздела «АДМИН».
- У профилей, созданных до появления механики, история согласий не подменяется: интерфейс честно сообщает, что состав документов при регистрации не был зафиксирован.

## 2026-08-08 Email verification for account registration

- Registration now requires a one-time email code sent through the configured SMTP transport. Codes are stored as hashes with a short expiry, resend cooldown and attempt limit; the code itself is never persisted or logged.
- The registration email is mandatory and unique across profiles. SMTP settings are read only from deployment environment variables and are not returned to the browser.
- The new-account form opens immediately. A promo code is optional: when supplied it is validated and applies its limits; when omitted, a verified email account is created through the open-registration code route.

## 2026-08-05 VK token secrecy and subscription persistence

- `getBotSettings` больше не возвращает User Token, Community Token или их массивы в браузер: для каждого сообщества доступны только `user_token_set` и `community_tokens_count`.
- Во вкладке НАСТРОЙКА токен вводится в закрытое поле, сохраняется отдельной операцией и сразу исчезает; вместо него показывается зелёный статус `Токен указан и сохранен в базе` и кнопка `Удалить`. После удаления показывается `Токен НЕ указан, укажите токен`.
- Каждый Community Token отображается отдельной статусной строкой без части или окончания секрета и удаляется отдельно по позиции; обычное сохранение настроек сообщества больше не перезаписывает сохранённые токены пустыми полями.
- Mini App сохраняет подписку через API до запроса разрешения сообщений VK. После серверного подтверждения React синхронно меняет кнопку на отписку; отказ или повторный ответ `VKWebAppAllowMessagesFromGroup` не отменяет сохранённую подписку и не блокирует переход.

## 2026-08-05 Control Center profile credentials and reliable launcher

- В локальном Центре управления добавлен блок `Данные входа профилей`: он загружает публичный список профилей и позволяет задать выбранному профилю новый логин, новый пароль и новую почту.

- Deployment читает `.env` тем же парсером dotenv, поэтому значения в кавычках и логины, начинающиеся со знака `#`, одинаково попадают в локальную синхронизацию и окружение Yandex Cloud.

## 2026-08-05 Mini App destinations after subscription actions

- Подписка и отписка Mini App выполняются строго в порядке: сначала сервер сохраняет и подтверждает запись пользователя, затем интерфейс синхронно показывает новую кнопку (`Отписаться` или `Подписаться`) и только после отрисовки открывает назначенный переход. Сервер не подтверждает действие, если сохранение не удалось или запись не изменилась.
- Исправлено открытие назначения: после успешной подписки или отписки сообщения сообщества, сообщество и собственная ссылка открываются отдельно от PAPA BOT Mini App, а вариант `Никуда` оставляет пользователя в приложении.
- Detail API и запросы Mini App отключают кеширование; когда пользователь возвращается из открытого назначения, приложение заново читает состояние подписки. Поэтому после успешной подписки остаётся состояние и кнопка `Отписаться`.
- Версия PAPA BOT обновлена до `version 005.0062.0025.0011.0021.0006.0004.0001.0003.0013.0013.0074.0001`.
- В редакторе каждой группы добавлены настройки `Куда отправить пользователя после Подписки` и `Куда отправить пользователя после Отписки`.
- Для каждого действия доступны варианты: `В сообщения с сообществом`, `В сообщество`, `Никуда` и `По ссылке`; последний вариант показывает поле собственной ссылки администратора.
- Новая группа и старые строки без настройки получают безопасное значение `Никуда`.
- Ссылки принимаются и передаются в Mini App только с протоколом `http` или `https`; другие схемы и пустая ссылка не сохраняются для перехода.
- Перенаправление выполняется только после успешного ответа API: в сообщения используется ссылка VK на диалог с сообществом, в сообщество — страница `club<ID>`, по ссылке — введённый URL.
- Регрессии проверяют редактор, сохранение, нормализацию данных и detail API, безопасные URL и порядок действий в Mini App.

## Архитектура и runtime

- PAPA BOT работает как queue-first система на Yandex Cloud Functions.
- Входящие события VK принимаются через `handler`, нормализуются и отправляются в очередь.
- Основная обработка событий выполняется через `workerHandler`.
- Отправка исходящих действий VK вынесена в `senderHandler`.
- Используются очереди для входящих событий и исходящих VK-действий.
- `message_new` обрабатывается классическим runtime сообщений, а `message_reply` проходит через structured triggers без запуска классического `handleMessage`.
- Реализована идемпотентность событий, чтобы повторная доставка не приводила к повторному выполнению действий.
- Используется hot-state/cache слой для ускорения чтения настроек, пользователей, переменных и runtime-данных.
- Сохранена совместимость с Google Sheets как источником/хранилищем конфигурации там, где это требуется текущей архитектурой.
- Есть отдельный планировщик для отложенных сообщений и рассылок.
- Есть служебные endpoints для health-check и получения текущих настроек.

## Captcha и безопасность админ-панели

- При подозрительной смене IP админская сессия требует session captcha.
- После успешной session captcha сервер атомарно создаёт новую админскую сессию на текущий IP и User-Agent, возвращает новый cookie и `X-Admin-Session` token, а старую сессию закрывает как заменённую после CAPTCHA одной записью session-store.
- Атомарная замена session-store не даёт вкладке ПРОФИЛЬ и другим защищённым запросам увидеть старое состояние сессии и повторно запросить CAPTCHA сразу после успешной проверки.
- Если после прохождения session captcha ещё приходят старые параллельные ответы от запросов со старым `X-Admin-Session`, админ-панель игнорирует их auth-ошибки и не открывает CAPTCHA поверх новой сессии.
- Новая сессия после session captcha имеет короткое окно IP-уточнения: при том же User-Agent сервер может принять и запомнить текущий видимый IP без повторной CAPTCHA, чтобы облачный/proxy IP-дрейф сразу после проверки не ломал вход во вкладку ПРОФИЛЬ.
- После успешного прохождения session captcha админ-панель выполняет полную перезагрузку страницы, чтобы заново и полностью прогрузить все вкладки, настройки и runtime-состояние.
- После удаления текущего сообщества админ-панель полностью перезагружается, чтобы сбросить локальное состояние и показать актуальные данные.
- После успешной `Автонастройка сервера ВК` уведомление показывает обратный отсчёт от 5 секунд до 0 и затем полностью перезагружает админ-панель.

## Recent runtime/UI notes

- VK Mini App groups MVP is implemented as a separate miniapp/ Vite/React frontend that opens links in the format vk.com/appXXXX#c=<vk_group_id>&g=<slug>, renders either the visible group list or a direct group card, requests VK community message permission before first subscribe, and toggles subscribe/unsubscribe through PAPA BOT API.
- On the first clean launch, VK Mini App shows a three-step interactive onboarding with progress, Back/Next controls, a clear completion action, legal links and an explanation of selection, subscription and subscription management. Completion is versioned in localStorage, and the walkthrough can always be reopened through «Как это работает».
- Public GitHub Pages builds use the production PAPA BOT API fallback when no Vite API variable is provided; subscription, unsubscription, group loading and VK Bridge permission requests have explicit timeouts so the button returns from «Сохраняем...» into a clear success or error state. Direct browser launches without signed VK launch parameters show a clear instruction to open the Mini App inside VK for a real subscription.
- Real VK Mini App subscribe/unsubscribe requests are verified on the backend with signed VK launch parameters and the deployed `VK_MINIAPP_SECRET`; the deployment whitelist includes the Mini App auth environment so production launches can confirm the VK user instead of rejecting valid app sessions.
- When VK opens the Mini App without a #c route during moderation or direct discovery, the frontend uses VITE_DEFAULT_COMMUNITY_ID to show the configured community's visible group list after onboarding. An empty list is rendered as an actionable state with an explanation and a button to reopen the walkthrough instead of a blank/static screen.
- PAPA BOT exposes Mini App public/read endpoints for community-scoped groups, hidden direct-link groups, signed launch-param subscription status reads, signed subscribe/unsubscribe mutations, and admin-only Mini App image upload for group icons/banners.
- The admin Groups UI includes Mini App visual fields per group: enabled, hidden from list, slug, user-facing title/description, icon URL/file, banner URL/file, subscribe button text, unsubscribe button text, separate destinations after subscribe/unsubscribe and generated Mini App link. Group action buttons share the compact group-action-btn sizing class.
- Mini App group rows are normalized by src/modules/miniapp-groups.js, VK launch signatures by src/modules/miniapp-auth.js, and image assets by src/modules/miniapp-assets.js; coverage lives in tests/miniapp-*.test.js plus tests/admin-panel-groups-ui.test.js.
- Payment button YooKassa webhooks are idempotent by `paymentId`: if a saved payment button record is already `succeeded` or `canceled` and has already attempted/sent its route answer, repeated `payment.succeeded` / `payment.canceled` webhooks or duplicate pending records are acknowledged/normalized but do not send the success/fail step again.
- Prodamus is supported for bot payment buttons only, not for PAPA BOT profile balance top-ups: a Prodamus button creates a signed payform URL from the admin profile payment integration and the public `prodamusWebhook` endpoint verifies `Sign` before routing the user to the configured success/fail bot step.
- Profile payment integration selection currently offers YooKassa, Prodamus, and Robokassa. Prodamus payform links use a 64-character sha256 hex signature sent as the `sign` URL parameter and pass the order amount both as `order_sum` and as the single `products[0][price]` cart item. Prodamus payform URL parameters are percent-encoded in Windows-1251 so Russian payment descriptions render correctly on payform pages. Payment buttons can set a `Номер заказа в Prodamus` prefix; PAPA BOT transliterates it to a readable ASCII order id prefix and appends the usual unique suffix. Prodamus `urlSuccess`/`urlReturn` are generated as PAPA BOT return-handler URLs with `prodamusReturn`, `profileId`, `integrationId`, `paymentId`, and expected outcome context; successful/failed payform returns redirect the browser to the VK dialog with the target community, and signed `_payform_*` return requests are also accepted as payment confirmation for routing the user to the configured bot/step. Prodamus integrations can set signature mode `demo` for non-live payform pages, which signs payform links and verifies webhooks with `secretKey + demo`; empty/`live` uses the normal secret key. Prodamus `urlNotification` is auto-filled from the current PAPA BOT service URL/`APP_URL`, and saved legacy webhook URLs are completed with `profileId` and `integrationId` when new payment links are created. `sys` is empty by default for the self-written integration unless the admin explicitly enters a Prodamus-issued system code.
- Robokassa is supported for bot payment buttons only, not for PAPA BOT profile balance top-ups. A Robokassa button creates a production signed payment link with a positive numeric `InvId`, configurable `MD5` / `SHA-256` / `SHA-512` signature algorithm, signed `Shp_profileId` / `Shp_integrationId` / `Shp_paymentId` routing parameters, and sanitized/truncated description text that matches Robokassa limits. `SuccessUrl2` / `FailUrl2` participate in `SignatureValue` as their original URL values without absent preceding modifiers; they are encoded separately for transport so one decode by a VK `open_link` does not split their query parameters into the outer Robokassa URL. Robokassa links do not include `IsTest` or `Receipt`; fiscalization must be configured outside this PAPA BOT integration.
- Robokassa success is confirmed only by the public `robokassaResult` ResultURL handler using `Пароль #2`; valid notifications return exact plain text `OK{InvId}`. The profile payment integration UI names the Robokassa credentials as `Идентификатор магазина`, `Пароль #1`, and `Пароль #2`, shows where to find them in the Robokassa shop technical settings, and auto-displays the current PAPA BOT Result URL for copying into Robokassa. ResultURL routing is idempotent by payment id with same-process duplicate locks, stale in-progress recovery, and failed-route retry so repeated callbacks do not duplicate already sent success answers.
- Robokassa browser returns use `robokassaReturn=success|failure`: success returns only redirect the browser to the VK dialog and do not confirm payment, while valid failure returns may route the configured fail bot/step as a best-effort browser flow. ResultURL success has priority over browser failure returns, and a later valid success can upgrade an earlier canceled/failure state.
- Incoming user messages do not run payment pending fallback before trigger matching; normal bot triggers such as `111` are handled by the message runtime, while payment success/failure delivery is handled by YooKassa webhooks. Message-trigger answers are sent directly by the incoming-message worker by default so they do not depend on a later outbound queue drain.
- Admin table editable textareas use one fixed visible height and hide inner scrollbars so placeholders for `Answer` and `Answer attachments` are visible when a bot or step row is created.
- A failed `check_consent` action is a mandatory gate: after the consent request is sent, later actions in the same structured trigger and classic message bots do not process the same incoming message.
- VK message document delivery preserves TLS verification while rewriting repeated `psv*.userapi.com` redirects to `psv*.vkuseraudio.net`, and retries transient upload HTTP 405 responses with a fresh VK message upload URL.
- Temporary strict-TLS chain failures during VK document download are retried up to five times. If all attempts fail, the consent message is not sent with zero or one document: the incoming event fails before `messages.send` and returns to the queue for an atomic retry of the complete two-document message.
- VK API errors while reading an existing source document, including an expired or revoked User Token, now stop delivery before `messages.send` instead of sending foreign document IDs that VK silently removes.
- Newly uploaded OPD, OPD policy, and public-offer documents are saved through the VK wall-document flow with community ownership (`doc-<group_id>_<id>`), so later consent messages can reuse them without reading the uploader's personal documents at runtime.

## 2026-08-09 — Приватные видео в сообщениях VK

- Видео, предназначенные для отправки в сообщениях, сохраняются через User Token как личные VK-видео с `privacy_view=nobody` и без `group_id`, поэтому они не добавляются в видеокаталог сообщества.
- Идентификатор `access_key` сохраняется во вложении `video<owner_id>_<video_id>_<access_key>`. При подготовке существующего видео ключ восстанавливается через `video.get`, но приватность больше не переключается в публичную через `video.edit`.
- VK может ограничить воспроизведение приватного видео у получателя. Если API не разрешит просмотр, сервис должен показать ошибку доставки, а не делать видео публичным автоматически.

## 2026-08-10 — Источник загрузки вложений

- В разделе «ПРОФИЛЬ» каждый профиль выбирает источник для изображений, документов и видео/клипов: «Пользователь», «Сообщество» или использование глобального правила.
- Центр управления PAPA BOT задаёт глобальные значения и отдельные значения выбранного профиля. Глобальное сохранение очищает индивидуальные переопределения, поэтому правило сразу действует для текущих и будущих профилей.
- Начальная глобальная политика: изображения — сообщество, документы — пользователь, видео/клипы — сообщество. Она применяется к загрузкам из Сообщений, Комментариев, Рассылки и Отложенных; фото для комментариев VK остаётся в обязательном wall-photo формате сообщества.
- Если служебное хранилище этих настроек временно недоступно, раздел «ПРОФИЛЬ» и отправка вложений продолжают работу с безопасной глобальной политикой по умолчанию.
- Для видео и клипов при источнике «Пользователь» отдельно задаётся приватность VK: «Все пользователи», «Только друзья», «Друзья и друзья друзей» или «Только я». По умолчанию выбрано «Все пользователи» (`privacy_view=all`), чтобы адресат сообщения мог воспроизвести вложение. Глобальная настройка и индивидуальное переопределение доступны в разделе «ПРОФИЛЬ» и Центре управления PAPA BOT.
- В карточке каждого сообщества профиля быстрый переход «Источник загрузки вложений» расположен сразу после «Платежные операции» и открывает соответствующий блок настроек.
- Все переходы по карте сообществ профиля прокручивают заголовок выбранного блока в центр окна и временно выделяют сам блок и его заголовок, чтобы пользователь сразу видел, куда он перешёл.
