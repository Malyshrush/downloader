# PAPA BOT - реестр реализованного функционала

Обновлено: 2026-05-19.

## Правило сопровождения

Этот файл является рабочим реестром уже реализованного функционала PAPA BOT.

Каждый раз, когда в проекте появляется, удаляется, переименовывается или заметно меняется пользовательский или системный функционал, нужно обновить этот файл в том же изменении. Перед финальной проверкой задачи нужно сверить затронутые зоны с этим реестром и поправить соответствующие разделы.

При изменениях функционала проверять минимум:

- `src/handler.js` - HTTP API, админские действия, загрузки, профиль, авторизация.
- `src/modules/*` - runtime сообщений, комментариев, триггеров, рассылок, переменных, пользователей, очередей.
- `adminPanelHTML.js` - интерфейс админ-панели.
- `tests/*.test.js` - контрактные и runtime-тесты, показывающие ожидаемое поведение.
- `bot-version.json`, `README.md`, `PROJECT_DOCUMENTATION.md` - публичное описание версии и архитектуры, если меняется внешний функционал.

## Архитектура и runtime

- PAPA BOT работает как queue-first система на Yandex Cloud Functions.
- Входящие события VK принимаются через `handler`, нормализуются и отправляются в очередь.
- Основная обработка событий выполняется через `workerHandler`.
- Отправка исходящих действий VK вынесена в `senderHandler`.
- Используются очереди для входящих событий и исходящих VK-действий.
- `message_new` обрабатывается классическим runtime сообщений, а `message_reply` проходит через structured triggers без запуска классического `handleMessage`.
- Реализована идемпотентность событий, чтобы повторная доставка не приводила к повторному выполнению действий.
- Используется hot-state/cache слой для ускорения чтения настроек, пользователей, переменных и runtime-данных.
- Сохранена совместимость с Google Sheets как источником/хранилищем конфигурации там, где это требуется текущей архитектурой.
- Есть отдельный планировщик для отложенных сообщений и рассылок.
- Есть служебные endpoints для health-check и получения текущих настроек.

## Captcha и безопасность админ-панели

- При подозрительной смене IP админская сессия требует session captcha.
- После успешной session captcha сервер атомарно создаёт новую админскую сессию на текущий IP и User-Agent, возвращает новый cookie и `X-Admin-Session` token, а старую сессию закрывает как заменённую после CAPTCHA одной записью session-store.
- Атомарная замена session-store не даёт вкладке ПРОФИЛЬ и другим защищённым запросам увидеть старое состояние сессии и повторно запросить CAPTCHA сразу после успешной проверки.
- Если после прохождения session captcha ещё приходят старые параллельные ответы от запросов со старым `X-Admin-Session`, админ-панель игнорирует их auth-ошибки и не открывает CAPTCHA поверх новой сессии.
- Новая сессия после session captcha имеет короткое окно IP-уточнения: при том же User-Agent сервер может принять и запомнить текущий видимый IP без повторной CAPTCHA, чтобы облачный/proxy IP-дрейф сразу после проверки не ломал вход во вкладку ПРОФИЛЬ.
- После успешного прохождения session captcha админ-панель выполняет полную перезагрузку страницы, чтобы заново и полностью прогрузить все вкладки, настройки и runtime-состояние.
- После удаления текущего сообщества админ-панель полностью перезагружается, чтобы сбросить локальное состояние и показать актуальные данные.
- После успешной `Автонастройка сервера ВК` уведомление показывает обратный отсчёт от 5 секунд до 0 и затем полностью перезагружает админ-панель.

## Согласия и документы согласий

- Реализовано runtime-хранилище согласий.
- Реализована запись согласия пользователя.
- Реализовано удаление согласия пользователя.

- В интерфейсе используется действие `Загрузить документ`.
- Загрузка документа использует тот же механизм, что вложения в разделе сообщений.
- Для файлов меньше 3.5 МБ используется загрузка через Yandex-side flow.
- Для файлов 3.5 МБ и больше используется Render upload flow.
- Реализована запись загруженного документа согласия.
- Реализована история версий документа согласия: каждый загруженный файл сохраняется как отдельная версия и виден в списке.
- Главный админ может удалить любую версию документа согласия из профиля любого админа в выбранном сообществе.
- В модалке вложений/документов есть picker документов из профиля.
- Picker документов из профиля ищет документы активного сообщества и по внутреннему ID сообщества, и по VK Group ID.
- Runtime согласий ищет последнюю версию документа и по внутреннему ID сообщества, и по VK Group ID.
- Согласие с ОПД считается связкой документов `Согласие с ОПД` + `Политика ОПД`: принятие сохраняет версии обоих документов, проверка требует актуальность обеих версий, а обновление любого из этих файлов заново отправляет пользователю запрос согласия.
- При первой автонастройке VK-сообщества создаются тестовые документы профиля для `Согласие с ОПД`, `Политика ОПД` и `Публичная оферта`.
- Шаблонный бот `Согласия` создаёт пять защищённых шагов: запрос ОПД/Политики ОПД с кнопками `Согласен с ОПД` и `Удалить Согласие с ОПД`, запрос Публичной оферты с кнопкой `Согласен с Офертой`, два шага подтверждения по кнопкам и шаг удаления согласия ОПД.
- Защищённые шаблонные шаги бота `Согласия` нельзя удалить через админ-панель или сохранение таблицы обычному админу; Главный Админ может удалить эти шаблонные шаги вручную.
- Есть контрактные тесты для документов согласий.

## Платежные интеграции

- В ПРОФИЛЬ над блоком `Документы` добавлен блок `Интеграции Платежных систем`.
- Администратор может добавлять, редактировать, удалять и сохранять платежные интеграции профиля.
- Поддержаны пресеты платежных систем: `ЮKassa / YooKassa`, `Prodamus`, `Robokassa`, `ЮMoney`, `Unitpay` и `Custom`.
- Форма платежной интеграции показывает только поля выбранной платежной системы, объясняет каждое поле (обязательность, зачем нужно и где взять) и не сохраняет интеграцию без обязательных реквизитов выбранного провайдера.
- В карточке сохраненной платежной интеграции есть кнопка `TEST`, которая проверяет выбранного провайдера и обязательные реквизиты через серверный endpoint `testProfilePaymentIntegration`.
- Платежные интеграции сохраняются в `profile_dashboard.json` в контейнере профиля как база для будущих кнопок оплаты и других сценариев приема платежей.
- Есть API `saveProfilePaymentIntegrations` для сохранения платежных интеграций профиля.
- В конструкторе клавиатуры добавлен тип кнопки `Оплата`: админ выбирает платежную интеграцию профиля, сумму, описание, а также бота и шаг перехода после успешной/неуспешной оплаты из выпадающих списков; при отправке сообщения, тестовой отправке, отложенной отправке или рассылке PAPA BOT создает платеж YooKassa и преобразует кнопку в `open_link` со ссылкой на оплату.
- В конструкторе клавиатуры ячейки кнопок показываются компактно в три строки: название, тип и ключевая деталь; подробные параметры редактируются в отдельном модальном редакторе кнопки без закрытия конструктора клавиатуры.
- Превью кнопок в конструкторе заливается по смыслу кнопки: цветные кнопки используют выбранный цвет, `Ссылка` отображается белой с иконкой, `Оплата` — оранжевой с иконкой.
- В конструкторе клавиатуры все ячейки сетки и кнопки действий редактора имеют одинаковый размер, чтобы длинные названия, ссылки и подписи не растягивали отдельные кнопки.
- Сохранение клавиатуры валидирует правила VK: не больше 5 кнопок в ряду, до 10 кнопок и 6 рядов для inline-клавиатуры, до 40 кнопок и 10 рядов для обычной клавиатуры; кнопки `Ссылка` и `Оплата` разрешены только в режиме `В сообщении`.
- Кнопка `⌨️ Кнопки` в таблице ответа становится зеленой только когда в сохраненной клавиатуре есть хотя бы одна кнопка.
- Ряд клавиатуры, где есть `Ссылка` или `Оплата`, допускает не больше 2 кнопок по правилам VK; перед отправкой PAPA BOT дополнительно делит старые сохраненные ряды на VK-безопасные.
- Кнопка `Импорт JSON` во вкладках сообщений, комментариев и рассылки открывает модальное окно с примером JSON, textarea для вставки кода, выбором режима импорта и кнопкой `Импорт`; ошибки JSON показываются прямо в окне со строкой/колонкой, а импорт поддерживает цветные, ссылочные и платежные кнопки.
- YooKassa webhook для платежных кнопок обрабатывает `payment.succeeded` и `payment.canceled` через реквизиты выбранной платежной интеграции профиля: после успешной оплаты пользователь переводится в настроенный success-бот/шаг, после отмененной оплаты - в настроенный fail-бот/шаг.
- При создании платежной кнопки PAPA BOT сохраняет pending-платеж профиля и на следующем входящем сообщении пользователя проверяет его статус в YooKassa, чтобы применить success/fail-переход даже если webhook еще не дошел.

- Payment button YooKassa webhooks are accepted either through the `yookassaWebhook` query parameter or by detecting `payment.succeeded` / `payment.canceled` in the POST body; successful/canceled routes immediately send the selected target bot step answer, and pending-payment fallback on the next user message uses the same send behavior.
- Row `Copy` buttons keep duplicating the row and also copy a JSON export of that row to the clipboard; message, comment, and mailing rows are exported in the same `version: 1` format accepted by `Импорт JSON`, including keyboard buttons.
- Admin tables pin the first navigation columns during horizontal scroll: `Бот` / `Шаг` / `Триггер` for messages and comments, `ID` / `ИМЯ` / `СОГЛАСИЯ` for users, and `№` / `ID Получателей` / `ГРУППА Получателей` for mailing.
- Admin table section headers use larger opaque black text so `ОСНОВНОЕ`, `УСЛОВИЯ ПРОВЕРКИ`, `ВЫПОЛНЯЕМЫЕ ДЕЙСТВИЯ`, `ПЕРЕМЕННЫЕ`, `СЦЕНАРИЙ`, `СИСТЕМНОЕ`, `УПРАВЛЕНИЕ`, and delete section labels remain readable.
- Admin table textarea cells can be resized diagonally in both width and height; the pinned mailing `№` column is wide enough to keep its textarea and `Copy` button usable.
- When an admin manually drags a table textarea wider or narrower, the admin panel resizes the whole column live during the drag, preserves the measured inner gap between the textarea edge and the column border, and recalculates pinned-column offsets.
- The `?` hint for the users table `_Согласия` service column explains that it is machine-readable consent JSON, when it is updated automatically, how version checks use it, and includes an example JSON structure.
- Comment rows in the admin panel expose only `ТЕКСТ` and `ФАЙЛ` trigger modes; the `КНОПКА` trigger mode is available only for messages because VK comments do not support message keyboard buttons.

## Recent runtime/UI notes

- VK Mini App groups MVP is implemented as a separate miniapp/ Vite/React frontend that opens links in the format vk.com/appXXXX#c=<vk_group_id>&g=<slug>, renders either the visible group list or a direct group card, requests VK community message permission before first subscribe, and toggles subscribe/unsubscribe through PAPA BOT API.
- When VK opens the Mini App without a #c route during moderation or direct discovery, the frontend can use VITE_DEFAULT_COMMUNITY_ID to show an explanatory PAPA BOT intro and the configured community's visible group list instead of a placeholder screen.
- PAPA BOT exposes Mini App public/read endpoints for community-scoped groups, hidden direct-link groups, signed launch-param subscription status reads, signed subscribe/unsubscribe mutations, and admin-only Mini App image upload for group icons/banners.
- The admin Groups UI includes Mini App visual fields per group: enabled, hidden from list, slug, user-facing title/description, icon URL/file, banner URL/file, subscribe button text, unsubscribe button text, and generated Mini App link. Group action buttons share the compact group-action-btn sizing class.
- Mini App group rows are normalized by src/modules/miniapp-groups.js, VK launch signatures by src/modules/miniapp-auth.js, and image assets by src/modules/miniapp-assets.js; coverage lives in tests/miniapp-*.test.js plus tests/admin-panel-groups-ui.test.js.
- Payment button YooKassa webhooks are idempotent by `paymentId`: if a saved payment button record is already `succeeded` or `canceled` and has already attempted/sent its route answer, repeated `payment.succeeded` / `payment.canceled` webhooks or duplicate pending records are acknowledged/normalized but do not send the success/fail step again.
- Incoming user messages do not run payment pending fallback before trigger matching; normal bot triggers such as `111` are handled by the message runtime, while payment success/failure delivery is handled by YooKassa webhooks. Message-trigger answers are sent directly by the incoming-message worker by default so they do not depend on a later outbound queue drain.
- Admin table editable textareas use one fixed visible height and hide inner scrollbars so placeholders for `Answer` and `Answer attachments` are visible when a bot or step row is created.
